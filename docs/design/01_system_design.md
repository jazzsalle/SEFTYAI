## 1. 설계 원칙 — 발주처 의견을 기능으로

| 발주처 의견 | 설계 반영 |
|---|---|
| "~O건 입니다"처럼 단순하면 안 됨. 과거 몇 mm일 때 어디가 침수됐는지 구체적으로 | 답변 블록을 **한 줄 결론 → 핵심 수치 → 어디·왜·언제 → 지금 할 일 → 근거 → 유사사례 → 후속 질문** 순으로 고정. 모든 수치는 원천 레코드(재해대장·침수흔적·보험·119·매뉴얼 쪽수)에 근거 칩으로 연결 |
| 담당자는 호우경보가 뜨면 무엇을 해야 할지 모름 → 대응절차 안내가 좋음 | 시작 화면 = **상황판**: 특보 → 매뉴얼 비상단계 자동 판정 → "지금 할 일" 체크리스트(담당·시한·쪽수) |
| 우리 급경사지가 어디? 왜 위험? 언제 위험해지지? 내가 뭘 해야 하지? | 위험·취약 객체 상세의 기본 레이아웃 = **어디 / 왜 / 언제 / 무엇을** 4카드. 질의 답변도 같은 구조 |
| 재난마스터 ID (유형코드)-(발생일)-(순번), 하나의 호우에 지역별 기록을 묶어야 | `1001-20200723-01` 형식(공식 재난코드) + 지역 기록 `{eventId}-{시군구코드}` 아래에 특보·119·피해·복구·침수흔적·상황보고 연결. **재난사건** 메뉴 신설 |
| 통계성 정보만 구축되면 의미 없음, 상황전파 메시지처럼 복합 정보 | 사건 타임라인(특보→대응→신고→보고), 119 신고 ↔ 인근 위험객체 관련성 판정, 강우 ↔ 매뉴얼 통제 기준·과거 피해 강우 비교 차트 |
| 실장·국장·지자체가 "별로다" 하면 끝 | 3분 골든패스(§4.3) 무결성 우선, 오답 대신 되묻기, 근거·검증필요 표기를 숨기지 않음 |
| 매뉴얼 개인정보는 민감정보 아님 | 매뉴얼 원문 표출, 단 비상연락망·전화번호는 제외(가림 처리) |

## 2. 범위

**포함** : 로그인(시연 계정) · 통합 탐색(상황판·Agent 대화·브리핑) · 우측 패널(지도·전체목록·객체 상세·재난사건 상세·근거 원문·기상특보) · 재난사건(재난마스터) · 대응 매뉴얼 · 데이터 출처 · 대화 이력 · 브리핑 항목 설정 · 내 권한 · 보고서 인쇄(A4/PDF)

## 3. 아키텍처

```
[브라우저]  Next.js App Router (React 19, KRDS 토큰 CSS, OpenLayers 10)
   │  ├─ 지도 타일 ─────────────▶ VWorld WMTS (Base/Satellite/Hybrid) ─ 실패 시 OSM 자동 폴백
   │  └─ /data/*.geojson (정적) : 행정경계·하천·소하천구역 (부산·영천·인제만)
   ▼
[Next.js Route Handlers — 서버 (Vercel icn1)]
   ├─ POST /api/agent/query     T3Q Agent 질의  ──(T3Q_AGENT_URL 설정 시 프록시)──▶ T3Q Agent API
   ├─ GET  /api/agent/detail    상세정보조회
   ├─ GET  /api/board           상황판
   ├─ GET  /api/weather         기상특보 (scenario | live) ──▶ 기상청 WthrWrnInfoService (키 서버 보관)
   ├─ GET  /api/docs            근거 원문
   ├─ GET  /api/events · /api/manual · /api/catalog · /api/fixtures/conversations
   ▼
[데이터 계층 (DAL)]  data/seed/*.json  ← 현재 (서버 번들, server-only)
                     supabase/schema.sql ← 전환 시 (Postgres + PostGIS)
```

- **계약 고정** : `src/lib/contract/agent.ts`(zod). 시연 응답 서버도 응답을 스스로 `AgentResponse.parse()`로 검증 → 실 T3Q 연계 시 base URL만 교체, 동일 스키마 통과 여부로 검수.
- **키 관리** : 기상청 키는 서버 환경변수(`KMA_SERVICE_KEY`), VWorld 키는 브라우저 타일 호출 특성상 공개(`NEXT_PUBLIC_VWORLD_KEY`) — **VWorld 콘솔에 배포 도메인 등록 필수**.
- **상태** : 대화 이력·체크리스트·브리핑 설정은 계정별 localStorage(시연). 첫 로그인 시 응답 서버로 생성한 시연 이력 자동 주입(다른 PC에서도 이력 화면이 비지 않음). 대응절차 담당자 수정본은 지역 매뉴얼별 localStorage(원문 추출본 위에 덧씌움, 내보내기/가져오기로 공유 — D36). 운영 전환 시 Supabase 테이블(§6.3).

## 5. Agent 응답 설계 (시연 응답 서버 = T3Q 계약 구현체)

### 5.1 의도 분류 (추측 금지)
프리셋 키 → 참조대상 → 키워드 우선순위. 질문 속 **지역(부산/영천/인제)·강우("시간당 70mm")를 조건으로 흡수**. 미분류 시 `clarify` (선택 칩 제시, 임의 답변 없음).

| intent | 트리거 예 | 구성 (composer) |
|---|---|---|
| briefing | 브리핑, 현재 상황 | 결론 + 5개 항목(기상·위험·유사·매뉴얼·119) + 강우 차트 |
| risk | 급경사지/지하차도/야영장… + 어디·위험·기준 | 우선순위 TOP3 어디·왜·언제·이력·정비 + 매뉴얼 현장조치 + 범주별 목록 |
| similar | 과거·비슷한·잠겼 | 유사도(유형·강우·지역·계절·피해유형) + "어느 정도 비에 어디가 잠겼나" + 침수흔적 지도 |
| manual | 해야 할 일·절차·매뉴얼 | 특보→단계 판정, 단계 조치(담당·시기·쪽수), 현장 통제 기준, 보고 주기 |
| report119 | 119·신고 | 신고 경과 타임라인, 유형·집중 시간대, 신고 지점 인근 관리대상 |
| event | 2020.7.23·초량·힌남노… | 재난마스터 요약, 피해·복구·보험·침수흔적, 사건 경과 타임라인 |
| river | 온천천·금호강·내린천… | 하천 정보, 주변 관리대상, 매뉴얼 통제 기준, **재해대장 하천 피해 이력** |
| object | 특정 객체명 / 참조대상 | 단일 객체 어디·왜·언제·무엇을 + 인근 신고·관리대상 |
| weather | 특보·강우·수위 | 특보·강우·수위·만조 + 임계치 차트 |

### 5.2 "지금 먼저 볼 곳" 우선순위
`점수 = 위험수준(상3·중2·하1)×10 + 등급가중(A·D·가=2, B·C·나=1)×6 + min(동일 읍면동 과거 피해,30)×0.5 + 진행 중 사건 관련 119 신고(반경 1km, 범주-사고유형 관련성 일치)×12 + 실좌표 2 − 샘플 20`
— 범주-사고유형 관련성 예 : 급경사지↔토사·낙석, 지하차도↔지하차도·차량, 야영장↔하천·고립

### 5.3 정직성 규칙
- 공개자료 기반 수치(2020.7.23 81.6mm/h, 사망 3명 등)는 **"(공개자료·검증필요)"** 를 본문에 표기
- 시연 사건(2026.10.2~ 호우)·119 신고값은 **"가상 시연"** 배지 — 119는 표준 21개 항목 구조는 실제, 값은 실제 피해 지점에 근거한 시연값
- 강우 미확보 사건은 유사도 강우항목을 중립 처리하고 "ASOS 연계 필요"를 안내
- 위치 근사(원천 좌표 없음) 객체는 "위치 근사" 배지

### 6.2 재난마스터 모델
```
Event(eventId = {재난코드}-{YYYYMMDD}-{순번}, typeCode, period, status, weather{advisories, hourly, max/total rain, source}, ndmsKey)
  └─ RegionRecord(regionRecordId = {eventId}-{시군구코드})

        ├─ floodTraces{records[centroid, depth, area]}

        ├─ situationReports[] → SituationReport
        └─ actions[], facts[]
  └─ similarCases{regionRecordId: [{eventId, score, breakdown[factor, weight, score, basis]}]}

```

## 8. 지도
- 배경 : VWorld WMTS (일반·흐리게·영상) — 타일 오류 6회 누적 시 OSM 폴백 + 상단 라벨로 원인 안내
- 공통 참조 레이어 : 시군구 경계(점선+라벨), 읍면동 경계(줌 11.5+), 하천 중심선(등급별 굵기·라벨), 실폭하천, 소하천구역
- 조회결과 레이어 : Agent가 반환한 객체만(9/17 결정) — 범주별 색·모양(지하차도 ▼, 재난사건 ◆), **POI + 설명 태그(이름·등급)**, 선택 링, 하이라이트 펄스
- 상호작용 : 답변 엔티티 칩 hover ↔ 지도 펄스, 지도 클릭 → 우측 상세 탭, 하천 클릭 → 하천 상세, 하천 엔티티 hover → 하천 강조

## 11. T3Q · 발주처 협의 필요 사항
1. **강우-피해 결합** : 수신 데이터에 강우 없음 → 사건 기간·시군구로 ASOS/AWS 결합 (재난 33건 중 강우 보유 3건)

3. 공간 API 주체 : T3Q Spatial API vs 아이타이쿤 (문서 간 상이)
4. 대화 맥락 : stateful vs stateless / 기상특보 필드 형식(`weather_alerts[]` vs `conditions[]`)
5. 재해대장 재난명 ↔ 사건 별칭표(D-15), 공개등급 코드(3값 vs 4값)
6. 급경사지 NDMS 전체 테이블, 건축물 지하공간 실데이터, 119 신고 요약 가공 범위
