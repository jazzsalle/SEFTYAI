# 재난마스터 이벤트 연계 규칙과 유사사례 산정 기준

작성: 2026-10-03 · 대상 데이터: `data/seed/events.json`, `reports_119.json`, `situation_reports.json`, `disaster_codes.json`

## 1. 왜 "재난마스터 ID"인가

행안부(김인건 사무관)가 요구한 것은 통계표가 아니라 **한 재난에 관한 모든 기록을 한 사건으로 묶는 키**다. 예를 들어 "최근 부산 호우 때 신고 내용과 침수흔적은?"이라는 질문에 답하려면 119 신고, 피해·복구, 침수흔적, 상황보고, 기상특보, 강우량이 같은 사건 ID로 이어져 있어야 한다. "과거에 어느 정도 비가 왔을 때 어디가 잠겼나"라는 질문도 마찬가지다.

```
재난마스터(eventId) ─┬─ weather(특보·강우: 사건 단위, 현재 사건은 지역별 시간강우)
                     ├─ regions[]  ← 지역 하위 레코드(regionRecordId = eventId-시군구코드)
                     │    ├─ damages.publicFacilityLedger   (재해대장: 시설·위치·피해액·복구비)
                     │    ├─ damages.publicFloodItems       (공공시설 침수 피해내역: 주소·개요)
                     │    ├─ damages.privateFacility        (사유시설: 주택 침수 동수, 읍면동별)
                     │    ├─ damages.insurance              (풍수해보험 침수 지급: 일자·구별)
                     │    ├─ floodTraces                    (침수흔적도: 지구·침수심·면적·좌표)
                     │    ├─ reports119[]  → reports_119.json
                     │    ├─ situationReports[] → situation_reports.json
                     │    └─ actions[] (시각·조치)
                     └─ ndmsKey (DSTR_YEAR, DSTR_TY_CD, DSTR_SN) ↔ NDMS·상황전파 TSD_EVT
```

## 2. ID 규칙

| 구분 | 형식 | 예시 | 근거 |
|---|---|---|---|
| eventId | `{재난유형코드}-{발생일}-{순번}` | `1001-20200723-01` | 02.재난코드 정보(47개 코드) |
| aliasId(표시용) | `{영문약어}-{발생일}-{순번}` | `RAIN-20200723-01` | 화면 표시용. 조인에는 쓰지 않음 |
| regionRecordId | `{eventId}-{시군구코드5}` | `1001-20200723-01-26000` | NDMS 복구 입력 방식(사건 1건, 지역별 입력) |
| 119 신고 | `R119-{eventId}-{순번3}` | `R119-1001-20261002-01-003` | 원천 `번호`(1W…)는 그대로 보존 |
| 상황보고 | `SR-{regionRecordId}-{순번\|M순번\|F1}` | `SR-1001-20261002-01-26000-M01` | 초기·중간=01..., 상황전파=M.., 최종=F1 |

- **발생일**은 NDMS `DSTR_BEGIN_DE`가 우선이다. NDMS에 없는 사건은 최초 특보 발효일, 그것도 없으면 최초 신고일을 쓴다.
- **순번**은 같은 날, 같은 유형 안에서 01부터 매긴다. 예를 들어 2026-10-02에 남부지방 호우가 `-01`, 강원 영서 호우가 `-02`다. 90~99는 훈련재난(`DSTR_RGST_TP=9`) 전용이며, 2026-07-28 인제 훈련 보고서가 `1001-20260728-90`이다.
- **복합재난**에는 NDMS가 붙인 대표코드를 쓴다(예: 1008 태풍ㆍ호우). 함께 일어난 유형은 `damageTags`와 제목에 남긴다.

## 3. 사건 동일성(데이터를 사건에 붙이는 규칙)

| 데이터 | 결속 키 | 비고 |
|---|---|---|
| 재해대장 | `재난명` 별칭 목록 + 지역(시도·시군구, 비어 있으면 주소) | '영천리'(단양), '부산리'(서산) 같은 지명 오매칭을 막기 위해 시도·시군구로 정확히 일치시킴 |
| 사유시설 피해내역 | `재난명` 별칭 + 주소 | 위로금·농기계 등 파생 재난명도 별칭으로 흡수(예: `9.19.~21. 호우 농기계(확정)`) |
| 공공시설 침수 피해내역 | `재난명` 별칭 + 주소 | 2020.7.23 부산은 재해대장에는 없고 여기에만 있음 |
| 침수흔적도 | 행정코드 앞자리(26/47230/51810) + `F_BEGIN_DE`가 [시작-1일, 종료+1일] 안에 들어올 것 | 재난명 표기가 제각각이라('우2020년 7월 23일 집중호' 등) 날짜로 결속 |
| 풍수해보험 | 지역 + `사고일자`가 [시작-1일, 종료+1일] 안에 들어올 것 | 성명·증권번호·상세주소는 제거하고 구·군 단위로만 집계 |
| 119 신고 | 신고일시가 사건 기간 안에 있고, 지역이 일치하고, 풍수해 유형일 것 | 실데이터를 받으면 `원인명`·유형코드로 1차 필터 → 기간·지역으로 결속 |
| 상황보고 | 보고서 사고일시·장소 | 장마형 장기 사건 안의 국지 보고(예: 2023.7.13 인제 낙석)는 그 사건의 지역 레코드에 귀속 |

## 4. 유사사례 점수(100점 만점)

| 요인 | 배점 | 계산 | UI "유사도 근거" 문구 예 |
|---|---|---|---|
| 재난유형 | 20 | 같은 코드 1.0 · 호우↔태풍ㆍ호우 0.7 · 태풍↔태풍ㆍ호우 0.7 · 호우↔홍수 0.8 · 호우↔산사태 0.6 · 호우↔태풍 0.5 | "호우 ↔ 호우" |
| 강우량 | 30 | 시간최대·누적 각각 `max(0, 1-|ln(a/b)|/ln3)`의 평균. 3배 차이가 나면 0점이다. **과거 강우가 미상이면 0.4로 고정하고 신뢰도를 '보통'으로 낮춤** | "시간최대 58.5↔81.6mm" |
| 지역 | 20 | 같은 시군구(부산은 광역) 1.0 · 지형유형(해안도시/내륙분지/산간)이 같으면 0.4 · 그 밖 0 | "같은 지역(부산광역시)" |
| 계절 | 10 | 월 차이 d에 대해 `max(0, 1-d/3)`, 시기 구분(장마 6~7월, 태풍·늦여름 8~10월)을 함께 표시 | "10월(태풍·늦여름) ↔ 9월" |
| 피해유형 | 20 | 지역 레코드 `damageTags`의 Jaccard 유사도 | "공통 피해유형: 지하공간침수, 하천범람" |

- 이 가중치는 seedkit `07_similarity_disclosure_accounts.json`의 요인군(기상·수문 46 / 공간·취약 28 / 피해 16 / 대응 10)을 5개 요인으로 다시 나눈 초안(`sim-v0.7`)이다. 대응 요인은 대응 기록이 쌓이면 추가한다.
- 제외 대상: 훈련재난, `synthetic=true` 사건, 재난코드 1099(기타).
- 결과는 events.json의 현재 사건마다 `similarCases[regionRecordId]` 아래에 상위 5건으로, `score`·`confidence`·`breakdown`을 함께 저장했다.

### 계산 예(현재 사건 `1001-20261002-01`, 부산 레코드)

| 순위 | 과거 사건 | 점수 | 유형 | 강우 | 지역 | 계절 | 피해 |
|---|---|---|---|---|---|---|---|
| 1 | 1001-20200723-01 (초량 지하차도) | 80.9 | 20 | 20.9 | 20 | 0 | 20 |
| 2 | 1001-20240919-01 (9.19~21 부산) | 68.7 | 20 | 12.0* | 20 | 6.7 | 10 |
| 3 | 1001-20140825-01 (8.25 부산) | 64.8 | 20 | 8.2 | 20 | 3.3 | 13.3 |

\* 강우 미상: 0.4 고정값, 신뢰도 '보통'. 2014.8.25는 시간 130mm 대 58.5mm로 2배 넘게 차이가 나서 미상 사건보다 강우 점수가 낮다. 의도한 동작이다.

## 5. UI 표시 권고

- 카드: `점수 80.9 · 신뢰도 높음`과 5개 요인 막대를 보여준다. 각 막대 툴팁에는 `basis`를 그대로 쓴다.
- 강우가 `rainfallSource = "공개자료 기반 추정(검증필요)"`이면 "검증 전 수치" 배지를 단다. synthetic 사건은 "시연용" 배지를 단다.
- 근거 링크: 유사 사건의 `regions[].floodTraces.records`(지도 점), `reports119`, `situationReports(F1)`로 바로 이동하게 한다.

## 6. 남은 과제

1. **강우**: 실제 사건 30건 중 강우값이 있는 사건은 3건뿐이다(2014.8.25와 2020.7.23은 공개자료 추정, 2023.10.8 인제는 보고서 원문 13mm). 기상청 ASOS(부산 159, 영천 281, 인제 211)의 사건 기간 1·3·6·12·24시간 최대값을 붙여야 강우 요인이 제대로 작동한다.
2. **119**: 실데이터(소방청, '26.12 공유 예정)가 들어오면 `원인명`·`긴급구조유형2명칭` 코드표로 풍수해만 거른다. 신고내용은 마스킹되어 유통되므로 요약 가공 방식은 협의가 필요하다.
3. **사건동일성 별칭 테이블**: 재해대장·피해내역·침수흔적도의 재난명 표기 차이를 T3Q와 합의해야 한다(seed 샘플 D-15 '미합의' 상태).
