## 0. 한눈에

**사실(확인)**

1. **재사용 열쇠에 계정이 없다.** 질문 글·질문 출처·query_context·함께 보낸 특보·참조·앞 답의 T3Q 대화 ID가 같으면, 24시간 안(그 기준지역에 특보 발효 중이면 1시간 안)에 받은 답을 즉시 다시 쓴다. → 시연 질문은 **화면에서 누를 경로 그대로** 미리 물어 두면 즉시 나온다.
2. **지금 예열은 기본 브리핑 4문항(BR-01~04) × 3지역뿐이다.** 지역 질문(질문 모음·시작 화면 = 출처 LIBRARY), 이어서 묻기, 조건 입력 질의는 예열할 길이 없다. 계정에 저장된 「내 브리핑 항목」도 보지 않는다.
3. **조건 편집 창으로 직접 넣는 조건은 재현이 잘 깨진다.** 강우·수위 칸은 입력한 순서(나중에 고친 칸은 맨 뒤)대로 열쇠에 들어가고, [적용]한 조건은 [조건 비우기] 전까지 **뒤의 모든 질문에 붙는다**(뒤 장면의 예열이 모두 빗나감).
4. **에이전트 답에는 근거 문서·쪽이 없다.** 녹화 121건 모두 `result.evidence_refs` 가 빈 배열이고 답 글에 쪽 표기가 없다. 문서·쪽은 T3Q-19 근거 조회(사건별 재해연보·재난연감 쪽, 약 2초)와 앱 대응절차(지자체 행동매뉴얼 p.N)에서만 나온다. **T3Q-19는 지금 화면 어디에서도 부르지 않는다.**
5. **`run.mjs --set demo` 는 오류 없이 70문(cq_variants)을 돈다.** set 이 regional 이 아니면 모두 cq 로 간다. 조건(기간·키워드·강우·수위)도 보내지 않는다.

### 1.3 재사용 열쇠 — `src/lib/server/jobs.ts`


- `canon`(L94-95)은 **객체 키만 정렬**한다. 배열(`disaster_types`·`detail.keywords`·`detail.conditions`)은 순서가 다르면 다른 열쇠.

- **장면당 4문항 이하**: 계정당 동시 4(R8)라 예열이 빗나가도 대기열에 걸리지 않고, 질문 모음의 「한꺼번에 보내기」 한도(4)와도 같다.

- **이어서 묻기 한 번에**: 지금 대화에서 앞 문항(`after`)의 완료 작업을 찾아 `ask({ question, source: "FOLLOW_UP", libraryId, followUp: { jobId, refs: [] } })`. 앞 답이 없으면 단추를 막는다. 참조 대상은 비운다(예열과 같게).
- 브리핑 장면은 탭이 아니라 [브리핑 시작](브리핑 현황판)을 쓴다. 브리핑 항목은 **정확히 4개**로 둔다(시작 화면 타일이 무작위 4개).
- 도움말 `help.ts` L30 의 "[+] 버튼 … 조건 시나리오" 문구를 이 탭에 맞춰 고친다(지금 없는 단추).

### 2.1 A0 — 코드 없이 할 때

1. 문항: 기존 문항 중 요구에 맞는 것을 쓴다(예: 부산 BS-01 지하차도·하천 500m, BS-02→BS-04 2020.7 침수흔적→복구, LB-FT-01·LB-FT-02 침수 이력·저지대 / 인제 IJ-01→IJ-04 급경사지→붕괴위험지구, LB-SLOPE-02 / 영천 YC-02→YC-04, LB-PLAN-01·LB-FT-03 개선지구 정비·침수흔적 — 고르기는 질문 설계 쪽 판단).

3. 예열: 시연 시작 1시간 안에 **같은 계정·같은 링크(같은 경로)** 로 한 번씩 눌러 두고 완료를 확인한다. 시연 때 다시 누르면 「이전 답변 재사용」으로 즉시 나온다.

5. 조건 질의: 3.2 의 순서표대로 입력하고 장면이 끝나면 [조건 비우기].

## 3. 요구 2 — 조건 입력 질의를 한 번에 재현

### 3.1 재사용 열쇠가 같아지려면

| 열쇠 성분 | 화면에서 정해지는 곳 | 같게 하려면 |
|---|---|---|
| 질문 글 | 문항 = `fillText(문항, 기준지역 이름)` / 입력창 = 입력 글(앞뒤 빈칸만 지움) | 같은 문항·같은 기준지역 이름. 직접 입력은 글자·빈칸까지 같게 |
| question_source | 경로(1.2 표) | 같은 경로로 누르기 |
| `region` | 기준지역 `condition.base` | 같은 단계·코드·이름(계정 기본값 권장) |
| `reference_time` | 조건 「기준시각」 → `YYYY-MM-DDTHH:mm:00+09:00` | 같은 분 |
| `disaster_types` | 조건 「재난유형」을 고르면 `[그 값]`, 「전체」면 문항 기본값(문항으로 보낼 때만) | 「전체」로 두거나 같은 값 |
| `period` | 발생기간 시작·끝(날짜) | 같은 날짜(한쪽만이면 다른 쪽 null) |
| `detail.warning_kind` · `warning_level` | 「특보 종류(입력)」 자유 글(앞뒤 빈칸 안 지움) · 주의보/경보 | 같은 글자·같은 값 |
| `detail.keywords` | 쉼표로 나눈 순서 | 같은 낱말·같은 순서 |
| `detail.conditions` | 입력한 칸 순서 `{item, label, value, unit, source_type:"MANUAL"}` (`queryContext.ts` L71) | **같은 칸·같은 값·같은 순서**, 칸 이름·단위 글자도 같게 |
| `weather_warnings` | AI 모드 켜진 브리핑 · 특보 참조 질문만 | AI 모드 끄기 · 특보 참조 해제 |
| reference · 대화 ID | 이어서 묻기의 참조 대상 · 앞 답의 T3Q 대화 | 참조 없이, 앞 질문도 예열 답의 재사용이어야 |

열쇠에 없는 것: 계정·역할·대화 번호·빠른질의 번호·브리핑 묶음 정보·문항 id·자동 조회 데이터.

### 3.2 진행자가 조건 편집 창에 직접 넣을 때의 함정

1. **순서** — 강우·수위 칸은 입력(또는 고친) 순서대로 배열에 붙는다. 고친 칸은 빼서 맨 뒤로 간다(`Composer.tsx` L166-171). 같은 값이어도 순서가 다르면 다른 열쇠.
2. **글자** — 특보 종류는 자유 입력, 키워드는 쉼표 순서, 기준시각은 분 단위.
3. **남는 조건** — [적용]한 조건은 세션 조건이라 [조건 비우기](L200) 전까지 뒤의 모든 질문(질문 모음·브리핑 포함)에 붙는다. 뒤 장면의 예열이 모두 빗나가고 질문 뜻도 바뀐다.
4. **예열 길 없음** — 지금 예열은 조건을 보낼 수 없다(1.4).
5. **무대 시간** — 칸 6~8개 입력에 30~60초.

→ 직접 입력을 꼭 보여 줘야 하면: 입력 순서표(예: 특보 종류 → 특보 단계 → 1시간 강우 → 하천 수위, 고치지 않기)를 정하고, 예열도 같은 순서로 하고(A0 이면 같은 손 입력), 장면 끝에 [조건 비우기].

### 3.3 방안 비교

| 안 | 내용 | 고칠 파일 · 크기 | 위험 |
|---|---|---|---|
| B1 진행자 직접 입력 | 3.2 순서표 + 사전 실행 | 없음 | 높음(순서·글자·남는 조건) |
| **B2 문항 조건 프리셋 · 그 질문에만 (권장)** | 시연 문항에 `cond`(조건 시나리오, R11). 누르면 그 질문에만 프리셋 조건을 붙여 보내고 **세션 조건은 그대로**. 프리셋이 있으면 기준지역만 세션 값, 나머지 조건은 프리셋 값만(섞지 않음 — 열쇠가 늘 같게) | `library.ts`(`CondPreset`·문항별 `cond` +15~30) · `session.tsx`(`SubmitArgs` 에 조건 덮어쓰기 +5) · `explore/page.tsx`(보내기 + 질문 말풍선 아래 보낸 조건 한 줄 +15~20) · `lib/conditions.ts` 새로(입력 칸 이름·단위 `ITEMS` 를 조건 창과 공용 +15/-6) | 낮음. 같은 문자열·같은 순서라 열쇠가 늘 같고 남는 조건이 없다 |
| B3 서버가 문항 id 로 프리셋을 붙임 | 접수 라우트가 `lib.cond` 를 합쳐 `buildQueryContext` | `route.ts` +6 · 예열도 같은 함수 | 열쇠 일치는 가장 확실하나 "사용자가 고르거나 입력한 것만 보낸다"(`queryContext.ts` 머리 주석·R6)와 어긋나 보임 → B2 권장 |

프리셋 모양(값은 질문 설계에서 정한다 — 여기서 수치를 지어내지 않음):

```ts
cond: { warningKind: "호우", warningLevel: "경보", conditions: [{ item: "RAIN_1H", value: /* 값 */ }, { item: "WATER_LEVEL", value: /* 값 */ }] }
// 보내는 모양: query_context.detail = { warning_kind, warning_level, conditions: [{ item, label, value, unit, source_type: "MANUAL" }] }
// weather_warnings 는 만들지 않는다(R6 — 특보는 기상청 실시간만)
```

- **표시**: 지금은 보낸 조건이 입력창 요약(「상황 상세정보 n개」·「사용자 입력 조건」 배지, `Composer.tsx` L41-49)에만 있고 턴에는 없다. 프리셋 질문은 세션 조건을 바꾸지 않으므로 **질문 말풍선 아래에 보낸 조건을 칸 이름·값·단위 그대로** 한 줄로 보인다(작업 `request.query_context.detail` 에서). 표기 문구는 사용자 결정.
- (선택 연출) 조건 창을 보여 주고 싶으면: 프리셋 문항을 누르면 조건 창을 프리셋 값으로 열고 [적용 후 보내기] → 보낸 뒤 원래 조건으로 되돌림. +20~30줄.
- **속도**: 조건 질의도 예열(4장)해야 답이 즉시 나온다. 자동 조회는 매핑이 있으면 1~2초(SIMILAR_EVENT 는 query_context 를 통째로 보내지만 설명서 v0.3 상 강우·특보 조건은 유사도에서 견주지 않는다).

## 4. 요구 3 — 시연 세트 예열

### 4.1 화면과 같은 열쇠가 되는 조건

- 계정 = 그 지역 지자체 담당자(지금 방식). 질문 글 = `fillText(문항, baseName(defaultBase(계정)))` — 「부산광역시」 「경상북도 영천시」 「강원특별자치도 인제군」. 진행자가 기준지역을 구·읍면동으로 바꾸면 빗나간다.
- 출처 = 화면에서 누를 경로(질문 모음·시작 화면·시연 탭 = LIBRARY, 브리핑 = BRIEFING, 이어서 = FOLLOW_UP).
- query_context = **라우트와 같은 함수** `buildQueryContext(계정, 화면과 같은 모양의 조건, 문항 disasterTypes, 질문 글)`. 조건 = `{ base: baseWire(defaultBase(계정)), disasterTypes: [], referenceTime: null, period: null, warningKind: null, warningLevel: null, keywords: [], conditions: [] }` + 프리셋(3.3 B2와 같은 규칙). 지금처럼 손으로 만들지 않는다.
- 특보 없음(AI 모드 끔) · 참조 없음 · 빠른질의 번호는 문항 값(열쇠엔 없지만 답 내용에 영향 가능).

### 4.2 고칠 곳

| 파일 | 내용 | 크기 |
|---|---|---|
| `lib/server/warmPlan.ts`(새) | 시연 세트 → 접수 목록(계정·질문 글·출처·문항 id·빠른질의·query_context) 순수 함수. 브리핑은 그 계정의 저장된 「내 브리핑 항목」을 읽어 같은 규칙(기본 문구 그대로인 항목만 문항으로)으로 | +40~60 |
| `api/admin/warm/route.ts` | Body 에 `set: "briefing" \| "demo"`(지역 체크는 그대로). demo 면 `warmPlan` 대로 `submitJob`. 이어서 묻기는 2단계(4.3) | +30~50 |
| `lib/adminTypes.ts` | `WarmItem` 에 set·장면·경로 | +5 |
| `(main)/admin/page.tsx` | 「시연 세트 예열」 단추 · 표(장면 순서·경로·조건·접수 결과·상태·**제공처 상태**·처리 시간). 「새로 질의」는 확인 창 | +40~70 |

최소 확장만 하려면: Body 에 `ids`(문항 id 목록)·`source` 만 더하고 `DEFAULT_BRIEFING` 대신 쓴다 — `route.ts` +10, 화면 +20. 단 조건·이어서 묻기는 예열 못 한다.

### 4.3 이어서 묻기 예열(2단계)

1. 1번 문항을 **같은 계정·같은 경로**로 접수 → 재사용 사본(또는 새 답) 행. 사본은 원래 답의 T3Q 대화 ID 를 물려받는다.
2. 그 행이 완료되면 `followUp: { jobId: 그 행, refs: [] }` 로 2번 접수 → 열쇠 = [접두 붙은 질문, FOLLOW_UP, query_context, 없음, 없음, 1번 원래 답의 대화 ID].
3. 시연: 진행자의 1번 = 같은 원래 답의 재사용 사본(같은 대화 ID) → 2번 열쇠가 같다.

주의:
- 1번이 **완료되기 전**에 2번을 접수하면 대화 ID 가 아직 없어 다른 열쇠 → 2단계는 1번 완료 뒤(운영자가 한 번 더 누르거나 화면이 자동으로).
- 앞 작업이 **다른 계정**이면 서버가 앞 작업을 못 찾아(jobs.ts L135) 접두·대화 ID 없이 보낸다 → 반드시 같은 계정의 행으로.
- 1번을 [새로 받기]하거나 「새로 질의」로 다시 예열하면 대화 ID 가 바뀐다 → 2번도 다시 예열.
- 이어서 묻기를 탭 단추(라이브러리 문항 id 포함)로 보낼지, 입력창(id 없음 → 재난유형 기본값 없음)으로 보낼지에 따라 query_context 가 다르다 → 예열은 화면에서 쓸 경로 하나에 맞춘다.

### 4.4 어느 계정으로 예열하나

| 계정 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **지역 담당자(지금 방식, 권장)** | 지역별 동시 4·전체 8. 진행 중 합류 가능. 이어서 묻기가 캐시를 빗나가 실제로 나가도 같은 사용자의 T3Q 대화 | 그 계정 질문 목록(로그인 때 최근 40건, `session.tsx` L312)에 예열 작업이 보이고, 15분 안에 끝난 것은 「새 답변」 표시 → 시연 때 목록을 접거나 "아침에 받아 둔 답"으로 설명 |
| 운영자 | 지역 계정 질문 목록이 깨끗 | 운영자 한 계정 동시 4 → 느림, 진행 중 합류 안 됨, 이어서 묻기가 빗나가면 다른 사용자의 T3Q 대화 ID 로 나감(T3Q 처리 미확인) |

### 4.5 시간·운영

- **가늠**: 시연 세트 30문 기준 — 전체 동시 8이면 4묶음 × 2~3.3분 ≈ 8~14분, 동시 3(지난 실측 조건)이면 10묶음 ≈ 21~33분, 이어서 묻기 2단계 +2~4분. 동시 8에서의 T3Q 처리 시간은 실측이 없다(단일 파드, 운영 `T3Q_MAX_GLOBAL` 값 확인 필요) → 리허설에서 잰다.
- **D5 1시간**: 그 기준지역에 특보(건조·강풍·풍랑 포함)가 있으면 1시간 넘은 답은 버린다(10_verification_brainstorm §3.5 L93). → 장면 순서대로 **지역별로 나눠** 예열(예열 화면의 지역 체크), 각 장면 시작 기준 1시간 안. 특보가 없으면 24시간.
- **한 번 예열하고 그 답을 쓴다** — 좋은 답이 나올 때까지 다시 묻지 않는다(답 고르기, 같은 문서 L94). 「새로 질의」는 D5·T3Q 변경 때만, 그때는 검증 대조를 다시.
- 예열 표에서 **제공처 상태가 SUCCESS/PARTIAL_SUCCESS 인지** 본다(아니면 재사용되지 않음).
- 운영관리 화면을 끝날 때까지 열어 둔다(크론 없음).
- 시연 중 T3Q 가 멈춰도 예열한 답은 DB 에서 그대로 나온다(지도 도형도 사본에 함께 복사). 자동 조회는 실패로 보이고 접수 응답이 최대 8초 늦어진다.

## 5. 요구 4 — 자동 조회 종류를 늘릴 때와 R25·R3

### 5.1 먼저 — 근거 문서·쪽은 어디서 나오나

- **에이전트 답**: 녹화 121건(역량질문 70 + 지역 51) 모두 `result.evidence_refs` 빈 배열, 답 글에 쪽 표기(p.N·쪽·페이지) 0건, `data_gaps` 는 행동매뉴얼 3건(`manual` NOT_IN_SOURCE)뿐.
- **T3Q-19 근거 조회**: 사건 ID(`object_id`)로 재해연보·재난연감 쪽(예: 「2020 재해연보」 p.153, 절 경로 「사건ID 목록 › 2020년 7.28.~8.11. 호우」, 인용 종류 TITLE_ONLY — 문단은 NOT_YET_BUILT). A 조사에서 지역 사건마다 2건씩 SUCCESS(부산 T10107-20200723-0001·T10105-20220903-0001, 인제 T10107-20200728-0001·T10105-20230809-0001, 영천 T10107-20240708-0001), 약 2초. **화면에서는 부르지 않는다**(데이터 프록시 화이트리스트에만 있음, `api/t3q/data/route.ts` L24).
- **앱 대응절차(보존 기능, 지자체 계정)**: 지자체 행동매뉴얼 원문의 현장조치 기준에 쪽이 있다 — 부산 지하차도 p.113·하상도로(온천천) p.119·주민대피 p.129, 인제 산간계곡 물놀이 지역 대피기준 p.58·인명피해 우려지역 p.37, 영천 지하차도 통제 기준 p.289·주민대피 p.57(`data/seed/manual_procedures.json` fieldActions, 원문 뷰어 `/api/docs`). **T3Q 답이 아니라 앱의 매뉴얼**이므로 화면·발표에서 구분한다.

### 5.2 새 종류를 더하려면 고칠 곳

1. `lib/library.ts` L6 `PreviewApi` + 문항별 고정 인자(`previewArgs`: 사건 ID·하천 ID).
2. `lib/server/preview.ts`: `PreviewItem.method` 가 "POST" 고정(L13) → GET 허용 · `SPEC`(L21-27)에 method·path(인자)·body(qc, 인자)·지역 필요 여부 · `runPreview`(L29-43)가 인자를 넘김 · 지역 거르기(L33)를 종류별로.
3. `components/answer/cards/GenericCard.tsx` `COLS`(L18-23)에 새 종류 열. 목록이 `result.items` 가 아니면(T3Q-16 `stations`, T3Q-13 구조) 새 카드.
4. `lib/labels.ts`: 열 이름(page·title·section_path·occurred_at·category 등)은 이미 있다. 값 코드 `TITLE_ONLY`·`AGGREGATE_ONLY` 는 `VALUE_KO`(L112)에 없다 → 열에서 빼거나 사전에 더한다(화면 영어 금지).
5. 시험: 문항 id → 요청 매핑 시험(하네스).
6. 접수 응답이 자동 조회를 기다리므로(1.5) 느린 종류(T3Q-19 약 2초)를 더하면 그 문항의 턴이 그만큼 늦게 뜬다.

## 9. 요약

시연 질문을 즉시 보이게 하는 열쇠는 "화면에서 누를 경로 그대로 미리 묻기"다. 재사용 열쇠(질문 글·출처·query_context·특보·참조·앞 답 대화 ID)에 계정이 없어 지역 담당자 계정으로 예열한 답을 그대로 쓰지만, 지금 예열은 기본 브리핑 4문항뿐이고 조건 편집 창의 직접 입력은 순서·남는 조건 때문에 재현이 깨지기 쉽다. 그래서 `library.ts` 에 시연 세트(장면·순서·경로·조건 프리셋)를 한 번 정의하고, 질문 모음 「재난담당자의 하루」 탭(한 번 누르기·이어서 묻기 한 번에), 그 질문에만 붙는 조건 프리셋, 같은 함수로 열쇠를 만드는 운영관리 「시연 세트 예열」(이어서 묻기 2단계, 특보 시 1시간), `run.mjs --set demo`(앱과 같은 요청 모양, 모르는 set 오류)를 권한다. 녹화된 에이전트 답에는 근거 문서·쪽이 없으므로 문서·쪽은 사건 상세에 T3Q-19 칸을 더해(약 2초, 클릭 경로라 R3·R25에 맞음) 보이고, 통제·대피 기준의 쪽은 앱 대응절차(지자체 매뉴얼)가 따로 가진다. 승인 전에는 기존 문항·주소 링크·같은 경로 사전 실행으로도 시연할 수 있으나 위험이 크다.
