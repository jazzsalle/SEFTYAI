- **창 셋** — 부산·인제·영천 지자체 계정을 창 하나씩 연다. 기준지역은 계정 기본값(부산광역시 · 강원특별자치도 인제군 · 경상북도 영천시) 그대로 둔다. 동구·연제구·온천천·북안면은 질문 글로만 좁힌다. AI 모드는 끄고 특보 참조도 하지 않는다(재사용 열쇠가 깨짐 — D §7).
- **새 질문은 질문 모음에 들어가야** 자동 조회가 붙고 SUGGEST 로 나간다(D A1/A2). 입력창에 직접 치면 USER 로 나가 자동 조회가 없다. 앱을 고치지 않는 경우(D A0)에는 질문 모음에 이미 있는 예비 13문과 IJ-2·YC-4(YC-01 원문), 기본 브리핑으로 동선을 짠다. 조건은 손으로 넣는다(§2.1). 이 경우 BS-3·YC-2 자리에는 LB-WARN-01(BS-3b·YC-2b)에 W30·W100 조건을 붙여 누른다.
- **예열** — 그 지역에 특보(종류 무관)가 있으면 1시간 넘은 답은 버린다(D5). 그래서 시연 시작 1시간 안에 지역별로 같은 계정·같은 경로·같은 조건으로 받아 둔다. 지금 앱 예열은 BR-01~04 뿐이다. 나머지는 D④(시연 세트 예열, 승인)나 A0(미리 누르기)로 한다. 예열 표에서 제공처 상태가 SUCCESS/PARTIAL_SUCCESS 인지 확인한다.
- **조건 질의** — D B2(문항에 조건 프리셋, 그 질문에만 붙음)가 승인되면 한 번 누름이다. 아니면 §2.1 순서대로 손으로 넣고 장면이 끝나면 [조건 비우기]를 누른다. 남은 조건은 뒤 질문에 모두 붙는다.
- **근거 쪽** — 지금 화면은 T3Q-19 를 부르지 않는다. 사건 상세에 «근거 조회» 칸(D⑤)이 들어가야 «2020 재해연보 p.153»이 화면에 뜬다(약 2초). 그 전에는 사건 상세에 피해·타임라인까지만 보인다.
- **BR-04(행동매뉴얼, QQ-03)** — 녹화 3건 모두 `manual NOT_IN_SOURCE` 였다. 부산 답은 특보를 가정했고, 인제·영천 답은 실시간 예보·수위를 썼다(C §9). 실시간을 빼라는 시연 조건과 맞지 않으므로 **시연 계정의 브리핑 항목을 BR-01~03 으로 두기를 권한다**(요구사항 원문 문항이라 사용자 결정). 브리핑 예열은 BR-01~03 에 그대로 맞는다. 매뉴얼 장면은 앱 대응절차(지자체 매뉴얼 원문 쪽 — T3Q 답 아님)로 보인다.
- **빈 자동 조회 주의** — 인제 BR-03 의 취약시설(지하차도 0)과 영천 BR-02 의 침수흔적(0건)은 «결과 없음»으로 뜬다. 무대 브리핑은 부산 창에서 한다.

## 4. 시험 방법 메모(다음 단계 러너에)

1. **요청 모양** — T3Q-01 ASYNC 로 `{question, question_source, query_context}` 를 보낸다. `query_context` = `query_context_draft` 그대로이고, `level` 은 `SIDO`·`SIGUNGU` 그대로다. `period`·`detail.keywords`·`detail.warning_kind/level` 도 그대로 넘긴다. `detail.conditions` 원소마다 `source_type: "MANUAL"` 을 붙인다(앱 `buildQueryContext` 와 같음). `weather_warnings`·`quick_query_id` 는 넣지 않는다(앱의 조건 입력은 만들지 않음). 지금 `run.mjs` `toRequest` 는 `period`·`keywords`·`conditions` 를 버리고, 특보가 있으면 `weather_warnings` 를 만든다(D §6.1). 이 세트는 그대로 넘기도록 고쳐야 조건 질의 시간이 의미를 가진다.
2. **자동 조회 시간** — `preview` 마다 `preview.ts` 와 같은 본문으로 Data API 를 부른다. RISK_AREA·RISK_FACILITY 는 `{data_group, region, page: {page: 1, size: 50}}`, FLOOD_TRACE 는 `{region, page: 50}`, PLAN 은 `{region, page: 20}`, SIMILAR_EVENT 는 `{query_context: (source_type 포함 최종 qc), page: 20}` 이다. ms·`total_count` 를 적고, SIMILAR_EVENT 는 §2.2 의 목표 사건 순위도 적는다. 목표 사건: E2020BS → T10107-20200723-0001 · E2023BS → T10107-20230821-0001 · E2020IJ → T10107-20200728-0001 · E2022YC → T10105-20220903-0001 · E2024YC → T10107-20240708-0001.
3. **순서·횟수** — 동시 3(지난 실측과 같은 조건)으로 돌린다. 주 질문 24는 서로 다른 때 두 번 잰다(흔들림 — 규칙 9). 예비 23·브리핑 9는 한 번 잰다. 이 러너는 앱 캐시를 채우지 않는다(예열 아님 — D §6.2).
4. **판정** — `meta.elapsed_ms` ≤ 90초 빠름 · ≥ 180초 느림(B 띠). status·data_gaps·refs 수·답 길이를 적고, 답 글에 문서명(재해연보·중기정비계획 총괄조서·지하차도 현황)이 나왔는지 본다. §3 대조값과 맞는지는 사람이 본다.
5. **결과로 바꿀 것** — 같은 요구를 덮는 예비가 주보다 빠르면 맞바꾼다. 두 번 다 180초를 넘는 질문은 무대 동선(★)에서 빼고 예열 전용으로 돌린다. 조건 있음/없음 쌍(BS-3/BS-3b · YC-2/YC-2b · YC-4/YC-4b)에서 조건과 키워드가 시간에 주는 영향을 본다.

## 6. 사용자 결정과 남은 위험

**사용자 결정이 필요한 것**

1. 새 질문을 질문 모음에 넣을지 — D A1(문항 추가) 또는 A2(「재난담당자의 하루」 탭). 넣지 않으면 새 질문에는 자동 조회가 붙지 않는다. 그때는 예비 13문 중심의 앱 수정 없는 동선으로 간다(§1.3).
2. 조건 질의 방식 — D B2(그 질문에만 붙는 프리셋) 또는 손 입력(§2.1 순서).
3. 예열 — D④(운영관리 「시연 세트 예열」) 또는 A0(같은 계정·같은 경로로 미리 누르기).
4. 근거 쪽 표시 — D⑤(사건 상세 «근거 조회» 칸). 없으면 «재해연보 p.N»은 화면에 뜨지 않는다.
5. 브리핑 BR-04 를 시연 계정 브리핑에서 뺄지(§1.3).
6. 가정 강우 값 30·20·100mm(지역 매뉴얼 기준 값을 빌림)와 조건 키워드에 연도를 넣는 방식.

| 답이 실시간 도구를 쓸 가능성 | 특보 조건 질문(BS-3·IJ-3·YC-2) | 글에 «지금·현재» 없음, 시험 답에서 실시간 수치가 나오는지 본다 |

## 7. 요약

부산·인제·영천을 넘나드는 「재난담당자의 하루」 7장면에 주 질문 24(지역마다 8)·예비 23·아침 브리핑 9, 모두 56문을 놓았다. 주 질문 가운데 14문이 조건 입력 질의다(특보+1시간 강우 3, 기간(+연도 키워드) 11). 22문은 누르는 순간 1초 안에 Data API 자동 조회가 뜬다. 10문은 근거로 재해연보 쪽(2020 p.153 · 2022 p.146 · 2023 p.148 · 2024 p.154)을 낸다. 모든 질문은 T3Q 가 정답을 확인한 역량질문 변형에서 나왔다. 9문은 녹화로 100초 이하가 확인된 모양이다. 자신 있는 점은 세 가지다. 세 지역 요구 주제(지하차도·도심하천·반지하·지정 사유·통제 기준·당시 조치 / 급경사지·산사태·야영장·계곡 / 소하천 지구·피해 이력·정비계획 연계)를 데이터로 확인한 사실 위에 짰다. 기간과 연도 키워드를 넣으면 목표 사건이 자동 조회 목록 3~14위에 들어와 사건 상세(당시 문자·특보·피해)로 0.5초에 이어진다는 것을 실측했다. 기본 브리핑은 지금 앱에서 그대로 예열된다. 위험도 있다. 15문(새 모양 7·느린 모양 8)은 시험과 예열이 필요하다. 새 질문의 자동 조회·조건 프리셋·시연 세트 예열·근거 쪽 표시는 모두 앱 변경(D A2·B2·④·⑤, 사용자 승인)에 달렸다. 반지하·야영장·인제/영천 «당시 조치»·소하천 정비계획은 원천이 없거나 빈약해 대신하는 자료로 답한다.
