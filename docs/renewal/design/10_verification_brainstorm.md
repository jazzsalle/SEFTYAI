## 1. 한 줄 결론(권장안)

**「녹화는 한 번, 판정은 몇 번이든」.** T3Q 원응답을 녹화본과 `sa_agent_jobs.raw`에 그대로 남기고, 그 위에 정답지(판 관리) · 판정기(규칙 판) · 사람 판정(별도 파일·표)을 겹쳐 돌린다. 11/5 전에는 개발 PC 하네스 + 엑셀 왕복으로 유엔이가 직접 검증하고, 시연 뒤에 같은 판정기를 운영관리 「정합성 검증」 탭으로 올려 검증 권한자가 개발 PC 없이 돌린다. 시각화 전후 「페이지」는 만들지 않는다.

이 결론이 뜻하는 것:

1. **T3Q를 다시 묻지 않고 재판정한다.** 정답지가 바뀌어도, 규칙을 고쳐도 녹화본(70+51건)과 `raw`로 다시 판정한다. 재실행(70문 약 50분, 단일 파드 부하)은 반복 안정도·회귀가 목적일 때만, T3Q와 합의한 시간대에만 한다.
2. **자동 판정의 범위를 값 종류로 정한다(D16).** 개편 전 결정 D33(2026-10-04, 「꼭 사람이 판정해야 하나」 → 정합/부정합/보류·조치 담당 자동)과 달리, 이 안은 **결정적 값 종류(정수·이름 집합·0/없음·기록 행·시각)는 자동 판정(규칙 n판)을 인정**하고, **서술·범위·셈법 차이·보류·뒤집기·최종 정오 확정은 사람**이 한다. 둘을 가르는 관문은 측정치 하나 — 「자동 일치인데 사람은 오답」 0건. 지금 `run.mjs`의 부분 문자열 대조는 B-08-v1(정답 12·21이 «2016-12-30»·«#ref:r21»에서 걸려 3/3 통과, 실제 답은 9·3·6)처럼 틀린 통과를 내므로 그대로는 「판정」이라 부를 수 없다. 자동 결과 이름에서 「정답·PASS」를 없애고 「값 찾음」 계열로 바꾼다.
3. **「직접 하도록」의 두 해석을 다 쓴다.** (ㄱ) 유엔이가 직접(하네스 → 운영관리 탭). (ㄴ) T3Q에 「서비스 경로(`query_context`)로 재실행한 기록 + 자기 채점(`cq_variant_runs/grades`)」을 정답지와 함께 제출하도록 요구(#16·#21)하고 유엔이는 표본 20문 안팎을 감사한다. (ㄴ)은 T3Q 부하와 일정을 T3Q가 지고, 유엔이 판정과 교차 비교가 **같은 실행**에서 가능해진다.
4. **유엔이 값은 전부 「유엔이 표시/판정/집계」 머리표를 달고 내부(하네스·운영관리·검증 자료)에만 둔다.** 지자체·정부기관 사용자 화면(답 카드·Data 카드·이력·브리핑)에는 아무것도 더하지 않는다(R0·R25). T3Q 봉투의 `meta.quality_status: "VERIFIED"`(모든 녹화에 있음)는 「T3Q 자체 표기」로만 적고 유엔이 결과 이름에 「검증됨」 같은 말을 쓰지 않는다.
5. **증적의 단위는 바이트가 아니라 문자열 해시다.** 녹화본은 `client.mjs`가 `JSON.parse`하고 `run.mjs`가 `JSON.stringify(…, null, 2)`로 다시 쓴 것이며 `raw`는 jsonb라 둘 다 「받은 바이트 그대로」가 아니다. 증적 키는 `response_id + sha256(result.answer 문자열)`로 두고(문자열 값은 두 저장 형식에서 불변), 새 녹화·새 작업부터 본문 글(`text`)의 sha256을 함께 기록한다.

**상태기계와 기록(D3)** — 상태: 초안 → 2인 판정 → 협의 → T3Q 회신 → 확정 또는 병기. 확정 뒤 수정은 **append-only**(`supersedes`로 이전 판정을 가리킴, 삭제 없음). 기록 필수 칸: 문항ID · response_id · 답 원문 해시(sha256(result.answer)) · 정답지 판 · 규칙 판 · 판정 · 사유 유형 · 책임 · 사유 글 · 판정자 계정ID·역할 · 시각 · 근거 위치. 협의 전 판정 둘을 모두 보존하고 **판정자 일치율**(단순 %)을 결과서에 싣는다. 다음 실행에서 답 해시·정답지 판이 같으면 「이전 판정(같은 답)」으로 미리 채운다.

**엑셀 왕복 규칙** — 엑셀은 **작업 사본이며 증적이 아니다**. 답 원문을 셀에 넣으면 `=`·`-`·`+`·`@`로 시작하는 줄(표 행 `| - |`)의 수식 해석, 「2024-07-10」 날짜 변환, 「1,881」 숫자 변환이 일어난다. 따라서 모든 셀을 문자열로 강제하고, `import_verdicts.mjs`는 **문항ID + response_id + 답 해시**가 모두 맞을 때만 판정·사유·책임 칸을 가져오며 셀의 원문은 신뢰하지 않는다. 판정·사유·책임은 데이터 유효성 목록, 판정자별 파일을 합치되 다른 판정은 둘 다 보존.

**이의 대장** — 「부분 정답」 이하 또는 「정답지 의심」 문항에 V-001… 함께 보낼 것: 정답지 판 · request_id·response_id·conversation_id · 실행 시각 · 사유 · 발췌. 사유가 「해석·범위」면 T3Q 시험 방식(`[조건]` 글 붙임)으로 1회 더 돌려 입력 경로 탓(①)인지 Agent 탓(②)인지 가린다. T3Q 회신은 정답지 수정(새 판) / Agent 수정(회귀로 확인) / 해석 수용(합의서 갱신). 비동기 결과가 하루만 보관되므로(`/tmp`) **실행 후 24시간 안에 1차 이의 송부**를 규칙으로 둔다(#20). 교차 채점: T3Q `cq_variant_runs_416.jsonl`을 받으면 같은 판정표로 채점해 `grades_416`과 견준다 — 지금 교차표(416 정답 56 중 유엔이 AUTO_PASS 35)는 **다른 실행**끼리라 「답이 달라서」와 「기준이 달라서」를 못 가른다.

### 4.4 반복 안정도와 시연 관문

- `run.mjs --repeat 3`로 같은 질문 3회. 표기는 비율이 아니라 **「3회 중 n회 핵심 값 같음」**. 실행별 판정을 모두 공개하고 문항 종합은 **최악값**. 「안정도는 자기 일관성이며 정답성이 아니다」를 자료에 적는다. 실례: A-02-v1 1/4→3/4, P07-01-v2 개선지구 14↔21, 인제 급경사지 311↔322.
- 반복 실행은 **동결 시작 뒤에만**(§3.4). 동결 전 실행은 §6 프롬프트 규칙 둘(「질문 범위 우선」·「지정 중 = 해제일 없음」)이 적용되면 무효가 된다. 「11/5 전 개선 적용 vs 동결」은 D15.
- 이어서 묻기 6문(A-14-g2·A-26-v2·D-01-v2·P09-02-g2·P09-03-v2·P09-04-g2)의 10/27 녹화는 `request`에 `conversation_id`가 없고 응답 `turn_no`가 1인 **단독 전송**이라 맥락 검증 근거로 무효다(A-14-g2는 한 자리 값 «10»으로 1/1 통과). `run.mjs` 의존 순서(§3.2 ⑥)를 넣기 전에는 「64 유효 + 6 맥락 없음」으로 보고한다.
- 무대 질문 관문 4개: (1) 기준값이 있다 (2) 3회 중 3회 핵심 값 같음 (3) 사람 판정 「정답」 (4) 표출 정합 통과. **관문 (1)에서 지금 바로 되는 것은 없다**: YC-03은 P07-04-v2와 「D·E인」/「D·E 인」 공백 하나가 다르고(cache_key·답이 달라질 수 있음), YC-01은 P06-07-v1과 문구가 같지만 CQ 조건은 「태풍 · 2022-09-07 09:00」이고 라이브러리 경로(`queryContext.ts`)는 사용자가 정하지 않으면 `reference_time`을 보내지 않는다. BS-01·LB-MSG-01·인제 LB-RISK-01도 같다. 5문 모두 「T3Q 확인 필요」(#22)로 둔다. 시연 질문 선정은 발표 구성이지 데이터 화면의 값 선택이 아니며, 70문·51문 전체 현황을 함께 공개한다(09는 51문 중 추천 32문).

### 4.6 상시 점검(정답지 없이 모든 운영 작업에, 규칙만) 【S~M】 시연 뒤

- **실행 위치**: `finish()` 안이 아니다 — `finish()`는 사용자의 `/api/agent/jobs/{id}` 폴링(`getJob → advance → finish`) 안에서 돌아 사용자 응답을 늦춘다. 점검은 **`sweepAny`(크론) 뒤 또는 운영자 조회(`/api/admin/jobs`) 때 비동기로** 계산해 별도 표 `sa_job_checks`(작업ID·규칙 판·결과 JSON)에 저장한다. 이것이 FUN-UFR-907001 「응답 검증 결과」 로그다(지금 「PoC 미구현」).
- 점검 항목: (가) 질문 되돌림(`result.question`·`question_source` = 보낸 것) (나) 표지 정합(`#ref:rN` ⊂ `refs`, 글에 안 나온 refs — `contract.test.ts` L44~48 규칙 함수를 공유) (다) 조건 밖 대상 — `refs[].map.key`가 행정코드(`legal_dong_code`·`sigungu_code`)인 것만 앞자리(시도 2·시군구 5·읍면동 8, `regionOf`와 같은 규칙)를 `query_context.region.admin_code`와 비교, T3Q 객체 ID(`slope_no`·`HZ-`·`SL-`)는 해석하지 않음. 녹화 재분석(스크립트, 재계산 일치): CQ refs 474개 중 행정코드 241개, 지역 밖 48개가 5개 답에 몰림(A-02-v2 25·P02-04-v2 10·B-08-g 6·P13-01-g1 5·C-08-v1 2, 이 중 4문은 범위 주의 문항) · 지역 답 584개(행정코드 259개) 중 지역 밖 0 (라) 한 표지에 서로 다른 이름 여럿(B-08-v1 r19) → 사람 확인 목록 (마) 미지원·고정 칸(`entities`·`result_groups`·`evidence_refs`·`follow_up_questions` 빈 배열, `context_used` 고정값, 계약 밖 칸 — 302001) (바) 정상 0건과 실패 구분(302004) · DB 표 이름 노출(06 #13) (사) 라이브러리 질문에서 `preview` 참조값과 다름 · 같은 질의의 이전 답과 핵심 수치가 다름(예열 BR-01~04 날짜별).
- 결과는 질의 현황 행 상세 「자동 점검」 줄, 추적로그 「응답 검증 결과」 열(907003 「관리자·검증 권한 보유자만」), 정합성 검증 › 실사용 점검에만. 사용자 답 카드는 바꾸지 않는다. 사용자 API(`/api/agent/jobs/{id}?full=1`)에 섞이지 않는지 권한 시험 하나.

### 4.7 운영관리 「정합성 검증」 — 직접 하는 방안의 단계

- **0단계(지금 ★, 하네스 + 엑셀)**: 개발자가 실행·판정 묶음을 만들고 비개발 담당자는 엑셀 작업 사본으로 판정한다.
- **1단계(시연 직후 【M】)**: 질의 현황 행 상세(지금 raw·request·preview·geo 서랍)에 「정답 대조」·「자동 점검」·「판정 메모」를 붙인다 — 실사용·시연 답을 같은 자리에서 판정. 저장은 옛 `sa_kv` verify 범위(운영자 전용, rev 충돌 확인) 또는 새 표. 서랍 라벨 `VIEWS`(「원응답 raw」·「보낸 요청 request」…)의 영어 병기는 `src/lib/labels.ts`로 정리(R18).
- **2단계(【L】)**: 전용 탭(정답지 · 실행 · 판정 세 칸 보기 · 실사용 점검 · 이의 대장 · 내보내기) — 목업·서버 표·실행 방식은 **부록 B**. 옛 「응답 검증」 흔적(`kvStore.ts` verify 범위, `globals.css .vf-*`)은 재사용하되 「[정답값 편집]」과 빨강 계열 `--c-dang-sub` 배경은 버린다.
- **선행 조건(D8)**: `jobs.ts` 캐시 조회(L166~175)는 `cache_key`·상태·시각만 보고 `source`·계정을 보지 않는다. 검증을 앱 엔진(`submitJob`, 출처 `검증` → T3Q `USER`)으로 돌리면 cache_key가 사용자 질문과 같아져 **24시간 동안 사용자가 검증 답을 받는다**. 조회에 `and source <> '검증'` 추가 + `medianMs()`·운영관리 p50/p90 SQL에서 제외가 **구현·승인되기 전에는 앱 엔진으로 검증 실행 금지**(하네스만).

## 6. 「시각화 적용 전후 페이지」는 만들지 않는다

1. 정답 대조(②)는 **답 원문**으로 한다. 에이전트 답은 시각화하지 않기로 했고(07 결론·R14 — 구조칸 37/37 빈 값), 시각화는 같은 요청이면 같은 결과를 주는 Data API 카드에만 쓰며 원값 표를 항상 함께 둔다. 「시각화 전/후」로 정답이 달라질 여지가 없다.
2. 검증에 필요한 것은 「받은 값이 화면에 그대로 나왔다」는 **③ 표출 정합 증적**이다. 이미 `verbatim.test.tsx`(렌더 글자 = 원문 평문, 칩 수 = refs 고유 표지 수)가 있고, 시연 뒤 【S】 `render/viz_values.test.tsx`를 더한다 — 녹화된 Data API 원응답으로 `components/viz/Charts.tsx`를 그려 표식마다 `aria-label`의 값 = 원응답 같은 항목 값(`fmtNum`, 반올림 없음), 표식 수 = 항목 수, 곁 원값 표 글자 = 원응답인지 확인(축 눈금 간추림은 표시 형식이라 제외). CI에서 매번.
3. 전후 캡처(`shots_viz.mjs`·`shots_viz2.mjs` → `reports/shots/viz/before_*`·`after_*`)는 디자인 승인 근거와 보고 「화면 개선」 절에만 쓰고 정합성 검증과 분리한다(D13). **다만 11/5 발표에는 「원응답 JSON → 화면 캡처 → 같음」 1장이 필요하다** — 별도 페이지가 아니라 근거표(#7) 부록의 한 절로 전후 캡처와 `verbatim`(뒤에 `viz_values`) 결과를 합치고 그 절에서 발표 1장을 뽑는다(§3.2 ⑤).
4. 운영관리 2단계에 선택으로 「표출 점검」(자동 조회 데이터가 있는 작업이면 같은 부품을 내부에서 그려 「그림 값 ↔ 원응답 값」 목록 자동 대조)을 둘 수 있다. 운영자 화면에만 있어 사용자 화면은 변하지 않는다.
