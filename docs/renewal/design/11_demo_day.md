## 0. 목적과 전제

### 0.1 목적

- 지역별 핵심 요구 셋을 T3Q 역량질의로 보인다. 부산은 도심 침수, 인제는 산사태·계곡 재해, 영천은 소하천 범람·침수다.
- 질문은 과거 데이터와 계획서를 찾는 RAG 기준이다. 답마다 근거 문서·쪽이나 원천 표·행을 붙일 수 있어야 한다.
- 녹화가 없으므로 기다리는 시간이 짧아야 한다. 그래서 세 가지를 쓴다: 자동 조회(1초), 예열(24시간 재사용), 빠른 질문 꼴.

### 2.1 지역별 흐름 — 답 → 판단 → 다음 질문

아래 «본 것»은 Data API 대조값이거나 지난 녹화 답이다. 실제 답은 실측 뒤 7장에서 확인한다.

**부산 — 초량 고리**
1. BS-1: 하천 500m 안 지하차도 22곳이 나온다. 통제 기준 수심은 5cm 12곳·15cm 10곳이다. 초량제1지하차도는 초량천 옆이고 5cm다.
   → «초량제1 일대가 왜 위험지구인가» → BS-2.
2. BS-2: 초량 개선지구는 침수위험 가등급이고 2023-03-29에 지정됐다. 사업은 2024~2028년 배수펌프장 1식·수문 1개소·관로 4.14km다. 주소가 «초량동1173(초량제1지하차도) 일원»이다.
   → «도심하천 쪽 기준은?» → BS-3.
3. BS-3: 온천천 연산교의 특보 지점은 세병교, 대응수위는 4.02/4.99다.
   → «초량은 실제로 잠긴 적이 있나» → BS-4.
4. BS-4: 초량1지구가 2020-07-23에 6시간 잠겼다. 원인은 «집중호우, 저지대지하도로, 배수불량»이다. 유사재난 5위 사건 행을 누르면 «2020 재해연보» p.153 이 나온다.
   → «최근 큰 비 때는 무엇을 알렸나» → BS-5.
5. BS-5: 2023-09-16 문자가 나온다. «부산 호우경보, 위험지역 대피», «온천천·수영강 하천 산책로 출입 금지», «반지하주택 … 즉시 지상으로 대피».
   → «오늘 경보가 내려진다면» → BS-6 + 대응절차 p.119(하상도로 30mm).
6. 하루 끝: 반지하 점검 → BS-7(예열한 답).

**인제 — 계곡 하천 고리**
1. IJ-1: 토석류 산사태취약지역은 인제읍 97 · 남면 54 · 기린면 40 순이다.
   → «계곡 하천 교량 지구는» → IJ-2.

### 2.2 ① 출근 장면 운영(지시 모음 반영)

- **브리핑을 먼저, AI 모드는 그 다음.**
  - [브리핑 시작]은 예열한 BR-01~03 을 즉시 보인다.
  - AI 모드가 켜진 채 누르면 그 지역 발효 특보가 함께 나가 열쇠가 바뀐다(D §1.2·§7-3). 특보가 있는 날에는 새로 질의(약 2분)가 된다.
  - 그래서 브리핑 뒤에 AI 모드를 켠다. 특보가 없으면 1문장이 온다(실측 9초). 특보가 있으면 특보마다 2문장이 온다(시험 55초).
  - 특보는 실시간 기상청 특보만 쓴다(가짜 특보 없음).
- **BR-04(행동매뉴얼)는 시연 계정 브리핑에서 뺀다.** 지시 모음에 따른 것이고, 사용자 확인이 필요하다. 넷째 칸 후보는 녹화가 빠른 질문 모음 원문이다.
  - 부산: BS-03 «가» 등급 지구(55초)
  - 인제: IJ-01(65초)
  - 영천: YC-01(85초)
  - 단, 브리핑 항목으로 넣은 새 글에는 자동 조회가 붙지 않는다(기본 문구에만 붙음, D §1.2). 브리핑 예열이 계정의 «내 브리핑 항목»을 읽지 않는 점도 고쳐야 맞는다(D §1.4).
- **질문 목록 정리** — AI 모드는 10분마다 점검 질의를 쌓는다(«AI 모드 · 이전 답변»). 무대에서는 목록을 접는다.

## 4. 조건 프리셋

모든 조건 질의는 아래 고정값으로 보낸다.
- 칸은 3개 이하이고, 순서를 바꾸지 않는다. 재사용 열쇠는 배열 순서까지 본다(D §3.2).
- 재난유형 칸은 «전체»로 두면 문항 기본값이 들어간다. 프리셋 질문은 조건표의 재난유형을 쓴다.
- `weather_warnings` 는 만들지 않는다. 특보는 기상청 실시간만 쓴다(R6).
- `conditions` 에는 서버가 `source_type: "MANUAL"` 을 붙인다.

## 5. 속도 전략

1. **자동 조회를 먼저 보인다.**
   - 44문 가운데 43문이 누르는 순간 Data API 표를 띄운다(IJ-8 만 없음). 가장 느린 것은 부산 위험지역 1.0초다.
   - 답을 기다리는 1~2분 동안 표 행을 누르면 상세(원천 표·행, 1.4초)가 열린다.
   - 사건 행을 누르면 피해·타임라인(0.4~1.8초)과 근거 쪽(약 2초)이 열린다.
   - 그래서 «근거는 1~3초, 해설은 1~2분» 순서로 설명한다.
2. **예열 — 화면 경로 그대로 미리 묻는다.**
   - 같은 계정·같은 경로(SUGGEST)·같은 조건이면 24시간 안의 답을 즉시 쓴다.
   - 그 지역에 특보(종류 무관)가 있으면 1시간 안의 답만 쓴다. 그래서 시연 시작 1시간 안에 지역별로 받아 둔다(D §4.5).
   - 지금 앱은 브리핑만 예열한다. 이 세트는 D④(운영관리 「시연 세트 예열」, 승인 대기)로 하거나, 승인 전에는 A0(같은 계정으로 같은 경로를 미리 누르기)로 한다.
   - 예열 표에서 제공처 상태가 SUCCESS·PARTIAL_SUCCESS 인지 확인한다.
3. **생방송 / 예열 나누기.**
   - ● 는 예열이 빗나가도 기다릴 만하다(10초 계단 85초 안팎).
   - ◐·○ 는 예열한 답만 무대에 쓴다.
   - 빗나가면 질문만 보내 두고 다음 순서로 넘어간다. 답은 비동기로 받아지므로 질문 목록에서 나중에 연다.
4. **조건 질의는 빠른 꼴에만 붙인다.**
   - 특보 조건을 넣은 5문은 중앙값 96초였고, 조건 때문에 느려진 예가 없었다(B §4).
   - 기간 조건은 «이름·날짜로 집은 사건» 꼴(YC-4 85·95, YC-5 원형 55)에 붙였다.
   - 조건 있음/없음 짝(BS-6/6b·IJ-6/6b·YC-6/6b)으로 조건의 시간 영향을 잰다.
5. **창 셋을 함께 쓴다.** T3Q 는 비동기다. 부산에서 ● 질문을 누르고 설명하는 동안 영천·인제 질문을 이어 누른다. 지역별 동시 4·전체 8 안에서 한다(D §4.4).
6. **열쇠 깨짐 점검표(D §7)를 무대 전에 확인한다.**
   - 기준지역 = 계정 기본값
   - 조건 비움([조건 비우기] — 프리셋 방식이면 해당 없음)
   - 브리핑 때 AI 모드 끔
   - 특보 참조 해제
   - [새로 받기] 누르지 않기
   - 같은 질문 3초 안 두 번 금지

## 6. 실측 방법(다음 단계 — Prep·시험)

### 6.1 러너 준비(`harness/cq/run.mjs` — D §6)

지금 러너가 이 세트를 바로 돌리지 못하는 까닭은 셋이다.
- `--set demo` 를 주면 70문(cq_variants)을 돈다.
- `toRequest` 는 `period`·`detail.keywords`·`detail.conditions` 를 버린다.
- 특보가 있으면 `weather_warnings` 를 만든다.

고칠 것은 다음과 같다.
1. `--set demo` 면 `demo_questions.json` 을 읽는다. 모르는 set 은 오류로 끝낸다.
2. `query_context_draft` 를 그대로 보낸다.
   - `level` 의 SGG 는 SIGUNGU 로 바꾼다(L20 표 그대로).
   - `period`·`detail.keywords`·`detail.warning_kind/level` 을 넘긴다.
   - `detail.conditions` 원소에 `source_type:"MANUAL"` 을 붙인다.
   - `weather_warnings`·`quick_query_id` 는 넣지 않는다.
3. `--preview` 면 원소의 `preview` 를 `preview.ts` 와 같은 본문으로 부른다.
   - RISK_AREA·RISK_FACILITY 는 지역 + size 50, FLOOD_TRACE 는 지역 + 50, PLAN 은 지역 + 20, SIMILAR_EVENT 는 query_context + 20 이다.
   - ms 와 `total_count` 를 적는다.
   - `target_event.id` 의 순위를 적는다.
4. 리포트 열: 장면 · role · live · `meta.elapsed_ms` · waitedMs · 자동 조회 ms(가장 느린 것) · 목표 사건 순위 · 답 글 문서명 정규식(`재해연보|총괄조서|중기정비계획|중기계획|지하차도 현황|홍수취약지구 현황|급경사지정보|사면정보`) · 쪽 정규식(`p\.\s?\d|쪽|페이지`) · data_gaps · refs 수 · 답 길이.

이 러너는 T3Q 를 직접 부르므로 앱 캐시를 채우지 않는다(예열 아님). 시간은 «예열이 빗나갔을 때 기다릴 시간»으로 읽는다.

### 6.2 순서·판정

- 동시 3(지난 실측과 같음)으로 돈다. **주 22문은 서로 다른 때 두 번**, 예비 22문은 한 번 잰다. 모두 66회다(B 규칙 9).
- 판정 기준은 T3Q `meta.elapsed_ms`(10초 계단)다.

| elapsed_ms | 판정 |
|---|---|
| ≤ 85초 | 생방송 후보 |
| 86~125초 | 예열하고, 생방송에는 예비를 쓴다 |
| ≥ 126초 | 예열 전용 |

- 두 번 잰 값의 차이가 30초를 넘으면 생방송에서 뺀다.
- 맞바꿈: 같은 장면의 예비가 주보다 빠르고 대조값이 맞으면 서로 바꾼다.
- 근거 요청형(BS-4b·IJ-4b·YC-4b)에서 답 글 쪽이 p.153·p.148·p.146 이 아니면 환각으로 적는다. 시연에서는 쓰지 않는다.
- 공백 질문(IJ-8b)과 자료 확인 질문(BS-7·BS-7b·IJ-7b)은 «자료 없음» 답이 나오면 무대에서 뺀다. 아니면 공백을 그대로 보이는 사례로만 쓴다(사용자 결정).
